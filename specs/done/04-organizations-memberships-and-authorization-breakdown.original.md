## Planner decisions (interpretation of the contract)

1. **Frozen surface is untouched.** The manifest (`endpoint_for`), all request/response schemas, the `Error` envelope, the `Storage` protocol's existing 18 methods, and `build_current_user`/`resolve_or_provision`/`build_user_context` are consumed as-published by Phase 03; no signature changes. Routers register **from the manifest entries themselves** (the `me.py` pattern) and take `build_organizations_router(storage, verifier)` / `build_members_router(storage, verifier)`, mirroring `build_me_router`.

2. **New storage compound `provision_organization` (explicit contract update, not smuggled).** Organization creation must atomically write org + **owner** membership + two audits, because the owner invariant (decision 3) has no repair path: sequential `create_organization` → `create_membership` under per-op transactions can crash between the writes, leaving a permanent ownerless org whose slug is consumed forever (retry → 409, no update/delete-organization exists). AGENTS.md ("provisioning … concurrency-sensitive: define and test atomicity") makes this the sanctioned move under the delivery-map review rule: an explicit addition to the **current** phase's contract. Shape mirrors `provision_user` exactly: frozen echo bundle `ProvisionedUser`-style `ProvisionedOrganization(organization, membership, audit_events)`; keyword-only `(organization=…, membership=…, audit_events=…)`; one `BEGIN IMMEDIATE` transaction over the existing `_insert_*_row` helpers; UNIQUE violations translate to `DuplicateEntityError(kind=organization_slug / entity_id)`; unknown `membership.user_id` → `ReferenceNotFoundError` (org and audit FKs are satisfied inside the batch); full rollback on every failure; storage mints nothing. **No race-convergence semantics** (unlike `provision_user`): a slug conflict is a plain 409, never a converge. Task 1 must also update the contract module docstring ("18 operations" → 19; reword the `get_user_by_external_identity` "no 19th method" sentence, which is about `resolve_external_identity` naming, so `test_storage_contract.py`'s docstring assertion keeps passing), the pinned-surface test (18→19 + name list), `docs/contracts.md` (docs change rule: same change as the contract), and add suite cases **before** any service relies on it (AGENTS.md). DynamoDB replication is a Phase 06 obligation carried by the contract docstring, same discipline as `provision_user`.

3. **Documented role policy (the phase spec's "explicit role policy"; spec-revision proposal, §4/§14).** Role rank is `viewer < member < admin < owner` (`ROLE_RANK: dict[MembershipRole, int]`). Reads (`GET /v1/organizations`, `GET /v1/organizations/{id}`, `GET .../members`) require an **active membership at rank ≥ viewer** (any role). Mutations (`POST .../members`, `DELETE .../members/{user_id}`) require rank ≥ **admin** (owner or admin). `POST /v1/organizations` requires only authentication; the creator becomes **owner** via the batch. **Owner invariants:** the `owner` role is (a) not grantable through the membership API, (b) not removable through it (nobody, including owners, can delete an owner membership), and (c) not changeable — enforced by policy plus the deliberate absence of any update method in storage. Consequences documented: leaving an organization you own is impossible; every org keeps exactly its creator/provisioner as owner; adding to a `disabled` membership's pair is a 409 (pair uniqueness covers it) and there is no re-enable path — `MembershipStatus.DISABLED` is never set by Phase 04 (no update op).

4. **Denial semantics: one 403, no existence oracle, auditable where the FK allows.** Unknown organization, inactive organization, missing membership, inactive membership, and insufficient role all answer **403 `forbidden` with one fixed message** ("you do not have permission to access this organization") — deliberately mirroring Phase 03 decision 9's pinned explicit-org branch (403, no oracle), so the two seams never disagree. `authorization.denied` is appended **whenever the organization row exists** (audit→organization FK is then satisfiable): metadata is exactly `{"reason": <no_membership|inactive_membership|inactive_organization|insufficient_role>, "operation": <manifest operation_id>}` — reason strings are the only vocabulary; no email, no `sub`, no token, no role of the caller beyond what the reason implies. Unknown-organization denials get the same 403 but **cannot be audited** (no FK target) — documented exception to AC 4; the cross-tenant acceptance cases use existing orgs. Audit-append failure propagates (fail-closed: a denial that cannot be audited is a 500, never a silent 403). Authentication failures (401) precede the dependency and are not authorization denials — no audit. A request that will be denied still auto-provisions a first-seen Cognito identity (authn precedes authz, spec §6) — consistent with `/v1/me`, documented.

5. **Path parameter is the tenant selector.** Org-scoped routes act on `{organization_id}` from the path; the `AuthorizationContext.organization_id` (earliest-active default from `build_current_user`) is **not** required to match — otherwise a user could only manage their earliest org. The reusable contract is keyed on the resolved context so Phase 05 can add the `api_key` branch: the dependency consumes `ResolvedIdentity` and checks membership of `context.actor_id` (a `usr_` this phase). Org-selection headers/params are not invented (no spec basis).

6. **Layering per AGENTS.md.** Pure authorization rules + audit-event builders + domain errors live in `src/app/services/authorization.py` (tenancy/audit business rules); the FastAPI wiring (compose `build_current_user` → classify access → denial audit → `HTTPException`) lives in `src/app/auth/organization_access.py` (authorization resolution); organization/member mutation rules live in the rewritten `src/app/services/{organization,member}.py` as **functions with injected `storage` and injectable `now`/`ids`** (the Phase 03 `identity.py` pattern — the class-based scaffold is dropped); HTTP status translation for service errors happens in the routers (`app/api`). Mapping table (frozen envelope codes, no new codes): `OrganizationTypeNotSelectableError`/`OwnerRoleNotAssignableError` → **400** `validation_error`; `MemberNotFoundError` (remove a non-member) / `TargetUserNotFoundError` (add an unknown `usr_`, translated from `ReferenceNotFoundError` — org FK is already proven by the dependency) → **404** `not_found`; `OrganizationSlugConflictError` (from `kind=organization_slug`), `MembershipConflictError` (from `kind=membership`), `OwnerMembershipImmutableError` → **409** `conflict`; `InvalidCursorError` from list endpoints → **400** `validation_error` (opaque client-supplied token is malformed/foreign); any other `StorageError` → **untranslated** → the frozen 500 `internal_error` handler (adapter text never echoed). Error messages are fixed strings; no identifiers in error bodies (IDs live in audits, not responses).

7. **Mutation audits (JSON-safe, secret-free, targets pinned).** `organization.created`: metadata `{"type": <org type>}`, target `organization`/new `org_`, actor the creator `usr_` — inside the `provision_organization` batch. `membership.created` (API add): metadata `{"role": <granted role>}`, target `membership`/new `mem_`, actor the admin `usr_`, organization the org — standalone `append_audit_event` **after** the successful write. `membership.removed`: metadata `{"role": <role at removal>}`, target `membership`/the removed `mem_` id (target_id is a plain string, no FK) — appended **after** the delete commits. Ordering rationale: a mutation that fails must not audit as success; a committed mutation whose audit append fails returns 500 with the mutation persisted — accepted, documented limitation (SQLite has no cross-call transaction; the compound batch is the only atomic unit).

8. **List projection.** Services return domain `Page[Organization]` / `Page[Membership]`; routers project to `Page[OrganizationResponse]` / `Page[MemberResponse]` field-by-field, preserving `limit` and `next_cursor` verbatim (cursors stay opaque). `MemberResponse` deliberately omits the `mem_` record id (frozen schema). Query binding: `Annotated[PageParams, Query()]` (FastAPI 0.141 supports Pydantic-model query params; pinned version range `>=0.115,<1`). `list_memberships` returns **all statuses** by contract — MemberResponse carries `status`, so disabled rows are visible in the list (documented, matches contract, no filter invented).

9. **Test strategy (mirrors Phase 03's proven stack).** Unit: stub `Storage` classes recording calls (zero-write proofs) for `services/{authorization,organization,member}.py`; SQLite-backed service tests on tmp files. Integration: `TestClient(create_app(routers=[...]))` with the signed-token fixtures + loopback `JwksTestServer` from `src/tests/support/cognito.py` (never live Cognito), real SQLite, and a `seed_user(storage, sub, …)`-style helper that creates user + identity (+ org/membership with a chosen role) directly — role-matrix users are seeded, not provisioned. **Audit assertions read the SQLite file directly** (no audit read surface in the contract; precedent: Phase 03 task 6's direct-row counts). Concurrency: `threading.Barrier`, no sleeps, 20 repeats, main-thread warm-up read before the barrier. Every cross-tenant case asserts both the 403 body equality (oracle-freedom) and the audit row.

## Definition of done check (maps to acceptance criteria)

- [ ] A user lists only memberships and cannot read another organization by guessed ID (tasks 4, 5 — list scoping + uniform-403 GET matrix)
- [ ] Only documented roles mutate organizations/memberships; out-of-policy attempts are denied consistently (tasks 2, 3, 4, 5 — decision-3 policy + byte-identical 403)
- [ ] Membership creation/removal is duplicate-safe and preserves documented owner invariants (tasks 1, 2, 5, 6 — 409 paths, owner immutability, barrier proofs)
- [ ] Authorized mutations create safe audit events; denials create `authorization.denied` without sensitive data (tasks 2, 4, 5, 6 — direct-row assertions + hygiene sweep; unknown-org no-FK exception documented per decision 4)
- [ ] Integration tests cover owner/admin/member/viewer decisions and cross-tenant denial for every endpoint (tasks 4, 5 — all six §14 endpoints of this phase)

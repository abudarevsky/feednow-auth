## Planner decisions (interpretation of the contract)

1. **Zero contract change; the suite is the oracle.** `contract.py` (19 methods) and `tests/storage_contract/suite.py` (60 adapter-neutral cases + its own isolation rules) are consumed **unchanged** — AC 2 forbids adapter-conditional tests, and the SQLite entry's AST/subprocess proofs (`test_sqlite_contract.py:47-148`) already pin that `suite.py` imports no driver. Phase 06 inherits exactly the Phase 05 escalation's "none new" obligation: the five api-key ops (`api_keys_key_id_unique`, revoke CAS included) are already suite cases. `app/storage/__init__.py` stays adapter-free (its docstring mandates it); `app.storage.dynamodb` is imported only by explicit submodule path.

2. **Multi-table layout, native keys where they enforce, one `unique_constraints` table where they don't.** DynamoDB enforces uniqueness only on a table's own key, so:
   - `users` PK `pk`=`usr_` id; `organizations` PK=`org_` id; `external_identities` PK=`extid_` id; `audit_events` PK=`aud_` id; `api_keys` PK=`key_` id — record-id (`kind="entity_id"`) conflicts are native `attribute_not_exists(pk)` failures on these.
   - `memberships` PK=`organization_id`, SK=`user_id` — the `(org,user)` pair uniqueness **and** `get_membership`/`delete_membership` tuple lookups are native; `mem_` record-id conflicts are not, so they get a constraint item.
   - `unique_constraints` table: PK `pk`=`<kind>#<normalized value>`, SK `sk`=`<entity id>`, attributes `kind`, `entity_id`, plus `user_id` on email/identity-tuple items so conflict resolution is a single GetItem. Enforced kinds: `user_email`, `organization_slug`, `external_identity` (`provider#subject#tenant` with the same `None`→`""` normalization as SQLite, decision 6), `api_key_key_id` (the §8 segment), `membership_id` (the `mem_` record id). Conditional put `attribute_not_exists(pk)` → `DuplicateEntityError(kind)`; a second identity/extid/api-key **record id** reuse across different PKs is caught the same way where the PK isn't the record id.
   - GSIs (all `ALL` projection so reads never need a second roundtrip): `memberships.by-organization` (PK `g_org`=org id, SK `g_created`=`created_at#mem_id`), `memberships.by-user` (PK `g_user`=user id, SK `g_org_created`=`org_created_at#org_id`), `api_keys.by-organization` (PK `g_org`=org id, SK `g_created`=`created_at#key_ id`). Sort keys embed the fixed-width sortable timestamp encoding (decision 6), so lexicographic order equals chronological order and the `(created_at, id)` tiebreaker is exact.
   - `list_user_organizations` orders by **organization** `created_at` and hides non-active memberships: the `by-user` SK carries `org_created_at`, denormalized onto the membership item at write time. This is safe because no organization update path exists in the frozen contract (created_at is immutable once written); `create_membership`/`provision_*` read or construct the org anyway. FilterExpression `membership_status = "active"` applies server-side; keyset semantics (decision 5) make filtered continuation correct.
   - Single-table design was **considered and rejected**: it buys nothing the conformance suite can observe, and generic `GSI1PK/GSI1SK` names would make the CDK-facing schema/IAM matrix (AC 5) harder to pin per access pattern. Multi-table mirrors the SQLite schema 1:1, which is exactly what behavior-parity review needs.
   - Table names carry a configurable `table_prefix` (factory kwarg, default `""`) so Phase 07 can parameterize `dev`/`staging`/`prod` and the test harness can isolate runs (decision 8).

3. **Every multi-item write is one `TransactWriteItems`; conflicts are classified by transaction-item name.** Each operation is a list of named transaction items (base put, constraint puts, `ConditionCheck`s for FK parents). `TransactionCanceledException` cancellation reasons carry per-item `ItemCollection`/`TypeName` back — the adapter classifies **by which named item failed its condition**: constraint item → its `DuplicateEntityKind`; base put → `entity_id`; parent `ConditionCheck` → `ReferenceNotFoundError`. This is how DynamoDB replicates SQLite's FK enforcement (contract docstring: "this docstring is the obligation for Phase 06 to replicate the checks inside its conditional writes") with no reads-before-writes TOCTOU. Ordering rule for `provision_user` (contract-pinned): an email **or** identity-tuple constraint failure is interpreted as spec §6's concurrent-first-login race → `DuplicateExternalIdentityError`, and `existing_user_id` is resolved by one GetItem on the winning constraint item after the rollback (else `None`); slug/membership-pair/record-id failures propagate as their own kinds. `provision_organization` differs **on purpose**: taken slug is a plain `DuplicateEntityError(organization_slug)` (no converge), unknown `membership.user_id` (the only parent not created in-batch) is a `ConditionCheck` → `ReferenceNotFoundError`. All-or-nothing rollback is transactional by construction; the caller-echo return contract (no read-back, no minting) is honored verbatim — the compound returns the caller's objects, exactly as SQLite does.
   Standalone single-item writes with no constraint/FK needs (e.g. `get_*`) are plain `GetItem`/`Query`; `revoke_api_key` is a standalone conditional `UpdateItem` (decision 4). `ThrottlingException`/transient faults translate to the base `StorageError` (retryable channel; **no new error classes** — inventing a 20th contract symbol is cross-phase smuggling). `ClientError` messages never propagate: translated errors carry fixed, log-safe text with no table names, item dumps, or request IDs (mirrors the contract's `args[0]` rule).

4. **`revoke_api_key` CAS mirrors SQLite field-for-field.** `UpdateItem` with condition `attribute_exists(pk) AND #status = 'active'`, setting **only** `status='revoked'` and `revoked_at=<caller value>` (SQLite `sqlite.py:1148-1156` sets exactly these two; the model has no `updated_at`). On `ConditionalCheckFailedException`: `GetItem` — missing → `EntityNotFoundError` (absence is absence); present (already revoked) → return the stored key with the **original** `revoked_at` (idempotent success). The race window (loser reads after winner commits) returns stored truth — same observable outcome as SQLite's blocked-then-zero-rowcount path, and the suite's barrier cases (`test_concurrent_revocations_preserve_the_first_revoked_at`) pin it under Local.

5. **Pagination translation: adapter-native opaque keyset cursors; `LastEvaluatedKey` never escapes.** The contract pins cursors as opaque and adapter-generated — DynamoDB cursors need not (and must not) byte-match SQLite's, and the suite never compares cursor bytes across adapters (it pins traversal, exact-final-page, foreign/garbage → `InvalidCursorError`). Adapter format: base64url JSON `{"scope": <dynamodb-local tag>, "resume": {<index pk/sk attrs of the LAST RETURNED item>}}`. The resume key is derived from the last **returned** item (not the raw `LastEvaluatedKey`, which may sit past filtered rows and would skip unvisited items — the suite's between-pages case forbids exactly that). Query loop: `Limit` = a fixed scan batch (constant `SCAN_BATCH = 100`, clamped by the effective page limit when larger is impossible to hit early), server-side filter, accumulate until `limit + 1` collected (probe-row pattern, same trim/`next_cursor`/`limit`-echo logic as `_build_page` in `sqlite.py:537`) or the segment is exhausted (`LastEvaluatedKey` None → final page → `next_cursor=None`). Scope tags are adapter-internal constants; a foreign-scope or malformed/tampered payload → `InvalidCursorError` with fixed messages, never a raw `ValueError`/`binascii.Error`/driver error.

6. **Value encodings: duplicate the SQLite text conventions, touch `sqlite.py` not at all.** Sortable timestamp `YYYY-MM-DDTHH:MM:SS.ffffffZ` (`encode_timestamp`, `sqlite.py:236-244`) is re-implemented inside `dynamodb.py` (with a cross-reference comment) rather than extracted into a shared module: `sqlite.py` is a completed Phase 02 contract surface and a byte-stable refactor for a 6-line function is unjustified churn (AGENTS.md: don't change a completed phase's contract to start this one). Tenant normalization identical (`None`↔`""`, lossless via `ProviderTenant min_length=1`). Enum/id/status attribute values are the same `str(...)` domain values SQLite stores, and every item → domain reconstruction goes through `model_validate` (corrupt stored values fail loudly). `scopes` and audit `metadata` are stored as **native DynamoDB L/M types** (list order preserved; map equality is order-insensitive — the contract's "round-trips exactly" is observable equality, which native types satisfy; JSON-text storage would be emulating SQLite for no behavioral gain).

7. **boto3 becomes a runtime dependency; the no-boto3 app-import proof stays green.** `pyproject.toml` gains `boto3>=1.35,<2` (production adapter code imports it at module top of `dynamodb.py` **only**); `uv.lock` updates in the same commit. `test_app_skeleton.py:102` (subprocess-isolated `import app.main; 'boto3' not in sys.modules`) must pass unchanged — nothing in `app.main`/api/auth/services imports the adapter; only explicit `from app.storage.dynamodb import open_dynamodb_storage` does. Factory shape: `open_dynamodb_storage(*, endpoint_url: str | None, region: str = "us-east-1", table_prefix: str = "", *, dynamodb_resource=None) -> DynamoDbStorage` with a `close()` (client shutdown) so both suite entries' fixtures can call it uniformly; the optional injected resource is the documented unit-test seam (no live calls). `create_app`/routers/services are untouched — AC 1 is structural, and task 9 adds an AST scan proving it repo-wide.

8. **DynamoDB Local harness: opt-in, env-gated, per-test table lifecycle.** Registration: pytest marker `dynamodb_local` in `pyproject.toml` (`--strict-config` is on). Gating: tests carrying the marker **skip with an explicit reason unless `FEEDNOW_DYNAMODB_LOCAL_ENDPOINT` is set** (e.g. `http://localhost:8000`) — default `uv run pytest` stays green on machines without Docker, and the phase's real evidence run sets it. Server: `-inMemory -sharedDb` (fixed dummy credentials in the harness; `-sharedDb` removes the per-credential database isolation footgun). Isolation per the suite's fixture contract ("initialized adapter with all tables empty, per test"): each test creates the seven tables under a fresh random prefix and deletes them on teardown — deterministic, no truncation races, DynamoDB Local create/delete is millisecond-fast in memory. `src/tests/support/dynamodb_local.py` owns: endpoint probe (skip if unreachable), `create_tables(prefix)/delete_tables(prefix)`, `make_dynamodb_storage(prefix)`. The runnable Docker command lands in `docs/operations.md` (task 1) and the phase doc (task 9). moto is explicitly **not** used (incomplete transaction/condition fidelity makes it a different oracle than real DynamoDB).

9. **Provisioning race under Local is a real concurrency proof, not a mock.** The suite's barrier cases (`test_concurrent_identical_provisions_yield_exactly_one_success`, concurrent revocations) run against DynamoDB Local unchanged in task 8's full-suite pass — DynamoDB Local ≥ 2.x supports `TransactWriteItems`/conditions with real serialization, so "exactly one winner, full rollback otherwise" is exercised on the transactional path itself. If Local's transaction behavior ever diverges observably from the contract, that is a **Phase 06 defect to fix in the adapter** (or an escalation if it proves to be a Local limitation) — never a suite edit (AC 2).

## Planner decisions (interpretation of the contract)

- **Dependencies.** Add exactly one runtime dependency: `pyjwt[crypto]>=2.13,<3` (spec §2 names "PyJWT or Authlib" — PyJWT chosen; the `crypto` extra brings `cryptography`, which tests also use for RSA keygen). Floor 2.13 is security-driven, not taste: 2.10.0 shipped the substring-`iss` bypass (CVE-2024-53861 / GHSA-75c5-xw7c-p5pm, fixed 2.10.1) that the task-3 prefix-trap test targets, and 2.13.0 bundles the JWKS non-HTTP(S)-scheme SSRF fix (GHSA-993g-76c3-p5m4), the `PyJWK` algorithm-binding allowlist-bypass fix (GHSA-jq35-7prp-9v3f), and the fetch-error-clears-cache fix (GHSA-fhv5-28vv-h8m8) — all directly on this phase's usage path. No `boto3`, no `httpx` in runtime deps (httpx stays dev-only), no authlib. The existing subprocess-isolated no-`boto3` import proof for `app.main` must stay green.
- **Token contract (access tokens only).** Required claims: `sub` (non-empty, ≤255 → `ProviderSubject`), `token_use == "access"` (ID/refresh tokens rejected), `exp` (plus `iat`/`nbf` when present) with a fixed 60-second leeway, issuer **exact-match** against the configured allowlist via the app's own explicit `iss in allowed_issuers` set-membership check — **not** PyJWT's `issuer=` option (defense in depth: the prefix-trap guarantee stays independent of the library; no prefix matching — a prefix-tolerant check is the classic Cognito issuer-spoof), `client_id` ∈ configured set (Cognito binds the app client in access tokens via `client_id`; `aud` is an ID-token claim and its absence is expected — decode with `options={"verify_aud": False}` pinned explicitly). `email` is **required**: `User.email` is unique and non-empty, and the §6 flow needs it; a token without `email` is rejected 401 and the app-client configuration obligation escalates to Phase 07. `display_name` = `username` claim when non-empty, else `sub`. Algorithm allowlist is exactly `["RS256"]` (kills `none`/HS256 confusion); `kid` header required. **Step 0 (re-baseline 2026-09-13, reviewer-approved):** the unverified JOSE header is inspected before any claim extraction — (a) `alg` must be the exact case-sensitive string `"RS256"` (missing/non-string/other → `TokenValidationError("token algorithm is not allowed")`; no `.upper()` normalization, RFC 7515 algs are case-sensitive), then (b) `kid` must be a non-empty string (→ fixed reason `"token header is missing the key id"`, moved from the post-issuer stage). Strictly better fail-fast: non-RS256 forgeries reject before claim parsing, issuer membership, and any network fetch; establishes no trust (stage-1 unverified parse already reads the same header bytes); the decode-time `algorithms=["RS256"]` mapping of `InvalidAlgorithmError` stays as unreachable-in-practice fail-closed redundancy.
- **JWKS.** URL derived as `{iss}/.well-known/jwks.json` (Cognito's OIDC-standard path); one `jwt.PyJWKClient(url, cache_keys=True)` per configured issuer, constructed lazily from the allowlist; key rotation is handled by PyJWKClient's refetch-on-unknown-kid; proactive TTL refresh is deferred (Phase 08 — do **not** use `cooldown_duration`, it is 2.14-only and outside the pinned range). JWKS unreachable → `TokenProviderUnavailableError` → HTTP 503 (the frozen envelope falls back to `internal_error`; messages never contain token material). The `JwksSource` protocol is **issuer-bound**: `signing_key(issuer: str, kid: str)` — with a plural allowlist, a kid-only lookup would force cross-issuer scanning, and two issuers may legitimately reuse a kid string; since this is a published handoff interface (task 7), the kid-only shape would become a breaking change in Phases 06/07.
- **Provider mapping.** `provider=cognito`, `provider_subject=sub`, `provider_tenant=None` — the Phase 01 model docstring pins that cognito carries no tenant dimension (storage normalizes `None`→`''` internally). The verifier knows nothing about domain types; the service maps `CognitoClaims` → the identity tuple, keeping the provider-specific layer swappable (delivery-map invariant: product services never require Cognito data).
- **ID generation (Phase 03's half of the Phase 01 deferral).** `usr_`/`org_`/`extid_`/`mem_`/`aud_` = prefix + `_` + `uuid4().hex` (32 lowercase hex chars validate against `ID_SUFFIX_PATTERN`; `uuid4` is `secrets`-backed — no new entropy dependency). The `key_` application ID and §8 `key_id` segment stay with Phase 05. Module: `app/services/idgen.py`, pure functions. Clock: **one** `utc_now()` read per provisioning request, shared by all five entities and the three audit events (consistent batch timestamps; storage mints nothing).
- **Default workspace derivation (spec §7).** Name: `"{display_name}'s Workspace"` (the spec's example shape). Slug: `f"personal-{user_id}"` — unique by construction (user IDs are unique), so provisioning never needs a slug-collision retry loop; readable, secret-free, and never derived from email (AGENTS.md). Flagged as a spec-revision proposal.
- **Resolution/provisioning flow.** `resolve_or_provision(storage, claims)`: `get_user_by_external_identity` → on `EntityNotFoundError` build the fully formed batch (User `active`; ExternalIdentity; Organization `personal`/`active`; Membership `owner`/`active`; audit events `user.created`, `organization.created`, `membership.created`) and call `provision_user` once. On `DuplicateExternalIdentityError` (the §6 concurrent-first-login race): re-read the identity — found → converge on the winner's user; still absent → genuine email collision → `ProvisioningConflictError` (→ 409). **Convergence happens only via the identity-tuple re-read (same `sub` found → winner); `error.existing_user_id` is never sufficient for convergence** — the Phase 02 adapter resolves it via an email fallback (`sqlite.py` `_resolve_provision_race_user_id`), so it is populated with a *stranger's* id in the not-a-race email-collision case, and the contract docstring's "converges without a second query" guidance is unsafe for that case; `existing_user_id` may serve only as a post-convergence cross-check. This implements Phase 02's escalation note (branch service-side, no `matched_by` discriminator smuggled into the contract). After any resolution: `user.status != active` → `DisabledUserError` (→ 403) with no storage mutation.
- **Audit pinning (metadata JSON-safe, secret-free).** `user.created` metadata `{"provider": "cognito"}`; `organization.created` `{"type": "personal"}`; `membership.created` `{"role": "owner"}`. Targets pinned for deterministic tests: `target_type`/`target_id` = `user`/the new `usr_`, `organization`/the new `org_`, `membership`/the new `mem_` respectively. Actor for all three: `actor_type="user"`, `actor_id=` the new `usr_` (self-provisioning), `organization_id=` the new personal org (its FK is satisfied inside the same `provision_user` transaction). No `sub`, no token, no email in metadata.
- **AuthorizationContext for humans (spec §10).** `organization_id` = the **earliest active** organization: `list_user_organizations(user_id, PageParams(limit=1))` — storage pins `(created_at, id)` ascending, so page 1 item 1 is deterministic; `roles` = `[get_membership(org, user).role]`; `scopes` = `[]`; `actor_type="user"`, `actor_id=user.id`. Zero active orgs → `NoActiveOrganizationError` (→ 403: authenticated but no tenancy context; impossible right after provisioning, reachable only once Phase 04 can disable orgs). The context builder takes an optional explicit `organization_id` parameter with **pinned Phase 03 semantics** (so Phase 04 layers org selection without changing the published interface): when provided, `get_membership(organization_id, user_id)` must resolve with the membership `active` **and** the organization `active`, else `NoActiveOrganizationError` (→ 403); when absent, the earliest-active rule applies unchanged. Both branches are exercised by task 4's stub tests — no undefined parameter path ships in a handoff interface.
- **DI and mounting.** Router factory `build_me_router(storage: Storage, verifier: AccessTokenVerifier) -> APIRouter` closes over dependencies; `create_app(routers=[...])` stays exactly as Phase 01 froze it; no import-time environment reads (Phase 01 boot contract). The published handoff interfaces are the `AccessTokenVerifier` protocol and the resolved `AuthorizationContext` — Phase 05's API-key path and future providers feed the same context builder.
- **Test strategy.** `src/tests/support/cognito.py`: RSA-2048 keygen, `sign_token(claims, *, kid, key, alg="RS256")` with claim overrides, `jwks_payload()`, and a stdlib `ThreadingHTTPServer` JWKS fixture on `127.0.0.1:0` with a request counter — the acceptance-sanctioned "signed fixtures or a JWKS test server" (never a live Cognito pool). Unit tests use targeted `Storage` stubs (recording call counts — this is how "rejected without storage mutation" is proven); service/provisioning tests use real SQLite via `open_sqlite_storage` on tmp files (WAL); concurrency uses thread barriers, never sleeps. The memory fake stays deferred — no Phase 03 unit-test need escapes stubs + SQLite (honoring the Phase 02 deferral explicitly).

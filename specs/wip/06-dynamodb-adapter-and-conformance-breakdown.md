## Planner decisions (interpretation of the contract)

1. **Zero contract change; the suite is the oracle.** `contract.py` (19 methods) and `tests/storage_contract/suite.py` (60 adapter-neutral cases; the isolation rules live in the SQLite entry, not `suite.py`) are consumed **unchanged** — AC 2 forbids adapter-conditional tests, and the SQLite entry's AST/subprocess proofs (`test_sqlite_contract.py:47-148`) already pin that `suite.py` imports no driver. Phase 06 inherits exactly the Phase 05 escalation's "none new" obligation: the five api-key ops (`api_keys_key_id_unique`, revoke CAS included) are already suite cases. `app/storage/__init__.py` stays adapter-free (its docstring mandates it); `app.storage.dynamodb` is imported only by explicit submodule path.

2. **Multi-table layout, native keys where they enforce, one `unique_constraints` table where they don't.** DynamoDB enforces uniqueness only on a table's own key, so:
   - `users` PK `pk`=`usr_` id; `organizations` PK=`org_` id; `external_identities` PK=`extid_` id; `audit_events` PK=`aud_` id; `api_keys` PK=`key_` id — record-id (`kind="entity_id"`) conflicts are native `attribute_not_exists(pk)` failures on these.
   - `memberships` PK=`organization_id`, SK=`user_id` — the `(org,user)` pair uniqueness **and** `get_membership`/`delete_membership` tuple lookups are native; `mem_` record-id conflicts are not, so they get a constraint item.
   - `unique_constraints` table: **key-only (partition key, no sort key)** — PK `pk`=`<kind>#<normalized value>`; item attributes `kind`, `entity_id`, plus `user_id` on email/identity-tuple items. Key-only is required, not cosmetic: every lookup where the entity id is *unknown* (`get_user_by_external_identity`, `get_api_key_by_key_id`, provision-conflict winner resolution) is a single `GetItem` by the constraint PK, and a sort key would defeat both goals — `GetItem` needs the full key, and two items sharing a PK under different SKs would silently break the uniqueness the table exists to enforce. Enforced items and the frozen `DuplicateEntityKind` each maps to: `user_email`, `organization_slug`, `external_identity` (`provider#subject#tenant` with the same `None`→`""` normalization as SQLite, decision 6), `api_key_id` (the §8 segment — the enum value is `API_KEY_ID = "api_key_id"`), and a `membership_id` guard item mapping to **`entity_id`** (the `mem_` record id; the `membership` kind belongs to the org/user pair, which is native on the base table, not a constraint item). Conditional put `attribute_not_exists(pk)` → `DuplicateEntityError(kind)`. Record-id conflicts on tables whose PK *is* the record id (users, organizations, external_identities, audit_events, api_keys) are native base-table `attribute_not_exists(pk)` failures → `entity_id`; the membership record id is the only non-PK record id, hence its guard item.
   - GSIs (all `ALL` projection so a Query over the indexed table is self-contained for payloads that live on it — `list_memberships` and `list_api_keys` need no read-back; the one list whose payload lives on a *different* table, `list_user_organizations`, is handled by decision 2's read-back bullet): `memberships.by-organization` (PK `g_org`=org id, SK `g_created`=`created_at#mem_id`), `memberships.by-user` (PK `g_user`=user id, SK `g_org_created`=`org_created_at#org_id`), `api_keys.by-organization` (PK `g_org`=org id, SK `g_created`=`created_at#key_ id`). Sort keys embed the fixed-width sortable timestamp encoding (decision 6), so lexicographic order equals chronological order and the `(created_at, id)` tiebreaker is exact.
   - `list_user_organizations` returns `Page[Organization]` — the full org payload (name, slug, type, status, created_at, updated_at) — while the indexed table is `memberships`. **Design choice: single `BatchGetItem` read-back per page** against the `organizations` base table, results reassembled into the GSI's `(org_created_at, org_id)` order; the page's membership items supply only ordering and org ids. **Batch-boundary rule:** the probe-row trim happens on the *membership* items first (decision 5's `limit + 1` accumulation → trim to `limit`), and only the **trimmed page's** ≤ `limit` org ids are read back — with `MAX_PAGE_LIMIT = 100` (`src/app/models/pagination.py:26`) that is ≤ 100 keys, always inside the BatchGetItem 100-key/4 MB caps; the probe row's Organization is never fetched (the cursor resumes from the last *returned* item, so its payload is unneeded; a naive `limit + 1`-key batch would `ValidationException` at `limit=100`, and the suite seeds no ≥100-membership user, so only this rule prevents it). Chosen over full-org-payload denormalization onto membership items: it keeps one source of truth (no snapshot-staleness obligation if an org update path ever lands), mirrors SQLite's join, and keeps the membership write items and provisioning transactions lean — one extra roundtrip per page is not suite-observable. A read-back miss is impossible (no org-delete path in the frozen contract) and is translated to the base `StorageError` with fixed text if ever observed.
   - `list_user_organizations` orders by **organization** `created_at` and hides non-active memberships: the `by-user` SK carries `org_created_at`, denormalized onto the membership item at write time. This is safe because no organization update path exists in the frozen contract (created_at is immutable once written); `create_membership`/`provision_*` read or construct the org anyway. FilterExpression `#status = 'active'` on the membership item's `status` attribute (placeholder required — `status` is a DynamoDB reserved word, decision 3's expression rule) applies server-side; keyset semantics (decision 5) make filtered continuation correct.
   - Single-table design was **considered and rejected**: it buys nothing the conformance suite can observe, and generic `GSI1PK/GSI1SK` names would make the CDK-facing schema/IAM matrix (AC 5) harder to pin per access pattern. Multi-table mirrors the SQLite schema 1:1, which is exactly what behavior-parity review needs.
   - Table names carry a configurable `table_prefix` (factory kwarg, default `""`) so Phase 07 can parameterize `dev`/`staging`/`prod` and the test harness can isolate runs (decision 8).

3. **Every multi-item write is one `TransactWriteItems`; conflicts are classified positionally.** `TransactItems` entries carry **no names** (the API has none) and cancellation reasons carry no item identity fields — so classification is by **index**: each operation submits its items in a fixed order (base puts, constraint puts, `ConditionCheck`s for FK parents) and keeps a parallel, same-ordered list of classification descriptors; on `TransactionCanceledException` the adapter zips `CancellationReasons` (documented as positionally aligned with the submitted `TransactItems`; the no-error code is the literal string `"None"`, entries are `Code`/`Message` only) and the **first `ConditionalCheckFailed` in submission order decides the error**: constraint item → its mapped `DuplicateEntityKind` (decision 2's table); base put → `entity_id`, **except the membership base put**, whose native PK+SK `attribute_not_exists` condition enforces the org/user pair → `membership`; parent `ConditionCheck` → `ReferenceNotFoundError`. Submission order mirrors SQLite's statement order (users → identities → organizations → memberships → api keys → audits), so a multi-failure race classifies identically on both adapters. This is how DynamoDB replicates SQLite's FK enforcement (contract docstring: "this docstring is the obligation for Phase 06 to replicate the checks inside its conditional writes") with no reads-before-writes TOCTOU. Ordering rule for `provision_user` (contract-pinned): an email **or** identity-tuple constraint failure is interpreted as spec §6's concurrent-first-login race → `DuplicateExternalIdentityError`, and `existing_user_id` is resolved by one `GetItem` on the winning constraint item (key-only table, decision 2 — the constraint PK is fully known from the failed write's own inputs) after the rollback (else `None`); slug/membership-pair/record-id failures propagate as their own kinds. `provision_organization` differs **on purpose**: taken slug is a plain `DuplicateEntityError(organization_slug)` (no converge), unknown `membership.user_id` (the only parent not created in-batch) is a `ConditionCheck` → `ReferenceNotFoundError`. All-or-nothing rollback is transactional by construction; the caller-echo return contract (no read-back, no minting) is honored verbatim — the compound returns the caller's objects, exactly as SQLite does.
   Standalone single-item writes with no constraint/FK needs (e.g. `get_*`) are plain `GetItem`/`Query`; `revoke_api_key` is a standalone conditional `UpdateItem` (decision 4). Transient cancellation codes are **not** domain conflicts: `TransactionConflict` (and the single-item `TransactionConflictException`/`TransactionInProgressException` `ClientError`s) are the DynamoDB analogue of SQLite's `busy_timeout` blocking, so the adapter **retries the whole transaction/conditional write a bounded number of times** — a racing loser then converges on the winner's committed rows and surfaces the stable conflict the suite's barrier cases pin (exactly one success + mapped loser error); retries exhausted, or `ThrottlingError`/`ProvisionedThroughputExceeded`, translate to the base `StorageError` (retryable channel; **no new error classes** — inventing a 20th contract symbol is cross-phase smuggling). `ClientError` messages never propagate: translated errors carry fixed, log-safe text with no table names, item dumps, or request IDs (mirrors the contract's `args[0]` rule). **Expression hygiene:** every attribute name referenced in any Condition/Update/KeyCondition/Filter expression goes through an `ExpressionAttributeNames` placeholder unconditionally — `status` is a reserved word (as are the stored-but-never-expression names `name`, `type`, `role`), and the blanket rule removes any need to audit the 573-word list.

4. **`revoke_api_key` CAS mirrors SQLite field-for-field.** `UpdateItem` with condition `attribute_exists(pk) AND #status = 'active'`, setting **only** `status='revoked'` and `revoked_at=<caller value>` (SQLite `sqlite.py:1148-1156` sets exactly these two; the model has no `updated_at`). On `ConditionalCheckFailedException`: `GetItem` — missing → `EntityNotFoundError` (absence is absence); present (already revoked) → return the stored key with the **original** `revoked_at` (idempotent success). The race window (loser reads after winner commits) returns stored truth — same observable outcome as SQLite's blocked-then-zero-rowcount path, and the suite's barrier cases (`test_concurrent_revocations_preserve_the_first_revoked_at`) pin it under Local.

5. **Pagination translation: adapter-native opaque keyset cursors; `LastEvaluatedKey` never escapes.** The contract pins cursors as opaque and adapter-generated — DynamoDB cursors need not (and must not) byte-match SQLite's, and the suite never compares cursor bytes across adapters (it pins traversal, exact-final-page, foreign/garbage → `InvalidCursorError`). Adapter format: base64url JSON `{"scope": <list-scope tag>, "resume": {<index pk/sk attrs of the LAST RETURNED item>}}`. The resume key is derived from the last **returned** item (not the raw `LastEvaluatedKey`, which may sit past filtered rows and would skip unvisited items — the suite's between-pages case forbids exactly that). Query loop: each `Query` call uses `Limit = SCAN_BATCH` (constant 100 — a scan batch, not the page size; the effective page limit may be smaller or larger and the loop simply keeps fetching), server-side filter, accumulate matches until `limit + 1` collected (probe-row pattern, same trim/`next_cursor`/`limit`-echo logic as `_build_page` in `sqlite.py:537`) or the segment is exhausted (`LastEvaluatedKey` None → final page → `next_cursor=None`). Scope tags are adapter-internal constants; a foreign-scope or malformed/tampered payload → `InvalidCursorError` with fixed messages, never a raw `ValueError`/`binascii.Error`/driver error.

6. **Value encodings: duplicate the SQLite text conventions, touch `sqlite.py` not at all.** Sortable timestamp `YYYY-MM-DDTHH:MM:SS.ffffffZ` (`encode_timestamp`, `sqlite.py:236-244`) is re-implemented inside `dynamodb.py` (with a cross-reference comment) rather than extracted into a shared module: `sqlite.py` is a completed Phase 02 contract surface and a byte-stable refactor for a 6-line function is unjustified churn (AGENTS.md: don't change a completed phase's contract to start this one). Tenant normalization identical (`None`↔`""`, lossless via `ProviderTenant min_length=1`). Enum/id/status attribute values are the same `str(...)` domain values SQLite stores, and every item → domain reconstruction goes through `model_validate` (corrupt stored values fail loudly). `scopes` and audit `metadata` are stored as **native DynamoDB L/M types** (list order preserved; map equality is order-insensitive — the contract's "round-trips exactly" is observable equality, which native types satisfy; JSON-text storage would be emulating SQLite for no behavioral gain).

7. **boto3 becomes a runtime dependency; the no-boto3 app-import proof stays green.** `pyproject.toml` gains `boto3>=1.35,<2` (production adapter code imports it at module top of `dynamodb.py` **only**); `uv.lock` updates in the same commit. `test_app_skeleton.py:102` (subprocess-isolated `import app.main; 'boto3' not in sys.modules`) must pass unchanged — nothing in `app.main`/api/auth/services imports the adapter; only explicit `from app.storage.dynamodb import open_dynamodb_storage` does. Factory shape (all keyword-only — one `*` marker; a second bare `*` mid-signature is a `SyntaxError`): `open_dynamodb_storage(*, endpoint_url: str | None = None, region: str = "us-east-1", table_prefix: str = "", dynamodb_resource=None) -> DynamoDbStorage` with a `close()` (client shutdown) so both suite entries' fixtures can call it uniformly; the optional injected resource is the documented unit-test seam (no live calls). `create_app`/routers/services are untouched — AC 1 is structural, and task 9 adds an AST scan proving it repo-wide.

8. **DynamoDB Local harness: opt-in, env-gated, per-test table lifecycle.** Registration: pytest marker `dynamodb_local` in `pyproject.toml`'s `markers` — `--strict-config` (on) validates ini keys, not marker use, and `--strict-markers` is **not** enabled, so registration is for warning hygiene under `-ra`, not a hard gate. Gating: tests carrying the marker **skip with an explicit reason unless `FEEDNOW_DYNAMODB_LOCAL_ENDPOINT` is set** (e.g. `http://localhost:8000`) — default `uv run pytest` stays green on machines without Docker, and the phase's real evidence run sets it. Server: `-inMemory -sharedDb` (fixed dummy credentials in the harness; `-sharedDb` removes the per-credential database isolation footgun). Isolation per the suite's fixture contract ("initialized adapter with all tables empty, per test"): each test creates the seven tables under a fresh random prefix and deletes them on teardown — deterministic, no truncation races, DynamoDB Local create/delete is millisecond-fast in memory. `src/tests/support/dynamodb_local.py` owns: endpoint probe (skip if unreachable), `create_tables(prefix)/delete_tables(prefix)`, `make_dynamodb_storage(prefix)`. The runnable Docker command lands in `docs/operations.md` (task 1) and the phase doc (task 9). moto is explicitly **not** used (incomplete transaction/condition fidelity makes it a different oracle than real DynamoDB).

9. **Provisioning race under Local is a real concurrency proof, not a mock.** The suite's barrier cases (`test_concurrent_identical_provisions_yield_exactly_one_success`, concurrent revocations) run against DynamoDB Local unchanged in task 8's full-suite pass — DynamoDB Local ≥ 2.x supports `TransactWriteItems`/conditions with real serialization, so "exactly one winner, full rollback otherwise" is exercised on the transactional path itself. If Local's transaction behavior ever diverges observably from the contract, that is a **Phase 06 defect to fix in the adapter** (or an escalation if it proves to be a Local limitation) — never a suite edit (AC 2).
